# RobustLight 替换模块路线诊断（2026-10-12）

## 结论与范围

替换 diffusion 的路线可行，但当前任务应表述为**部分观测下、面向闭环控制的在线状态恢复**，不能仅以离线缺值填补误差判断成功。已经定位并用同一 checkpoint 的受控实验验证了一个实质瓶颈：ImputeFormer 的 self-conditioning 训练与运行时递归历史并不等价，把预测重新标成已观测会放大误差。

本次工作包含论文与代码审计、固定轨迹诊断、CPU 闭环评估。未修改训练、恢复器和控制器代码，也未启动新的训练。评估使用冻结副本，原有训练继续运行；副本保存在 `results/audit_20261012/{baseline,selfcond}.pt`。原始结果见同目录 `closed_loop.json`、`offline_diagnostics.json` 和日志。

这里的数值是单次诊断，不能代替多训练种子实验。论文 RobustLight 列是作者报告结果，本次没有重跑 diffusion。

## 1. 对原论文的理解需要修正

原文：[RobustLight, ICML 2025 / PMLR 267](https://proceedings.mlr.press/v267/li25cs.html)，[PDF](https://raw.githubusercontent.com/mlresearch/v267/main/assets/li25cs/li25cs.pdf)。本次直接核对了 §3.2、§3.4、Algorithm 1–2、Table 2、Table 10。

- RePaint 确实负责根据已知数据恢复缺失状态，模型可以被其他恢复器替换。
- 但 DSI 不只是纯监督扩散填补。论文定义了以历史状态和上一动作作为条件的 actor/critic，以及奖励驱动的梯度更新；Eq.12 使用预测历史计算后续步损失，处理累积误差。
- 官方实现 `refs/RobustLight/inferences/rl_dynamic_state_filling.py:621` 有 `action_gradient`，`:647` 起有 critic 更新和递归状态训练；`:695` 附近将 `state_recon` 写入下一步训练条件。
- Table 10 的历史条件长度为 4，non-Markovian step 为 6。当前 IF 窗口长 24，属于不同的历史长度配置，需要披露并做预算/窗口消融。

**旧文档 `docs/audit/reuse_audit.md` 关于 RobustLight“无决策感知训练”的概括不准确。** 可以说本项目拟采用不同的决策损失，但不能把“首次让恢复过程考虑控制目标”作为相对 RobustLight 的创新。是否构成对其他论文的新贡献还需要独立文献核查；本次没有审计旧文档的其他文献结论。

论文基准本身同时包含传统 MaxPressure 与 RL 控制器。因此先在 MaxPressure 上验证替代模块是合理子任务，不必为了对标而立即训练 RL。但仅做 MaxPressure＋缺失场景，不等于覆盖论文的所有攻击与控制器。

## 2. 当前 CityFlow 基准已具备对齐证据

`experiments/if_recover/eval_closed.py` 与官方 `utils/model_test.py` 的 MaxPressure 缺失分支对齐了：3600 秒仿真、15 秒决策、5 秒黄灯、四相位、方向维度映射、在 `step_num >= 4` 后回写损坏状态、官方 ATT 聚合方式。

此次重跑无恢复基线：

| 数据集 | 缺失方向 | 本地 ATT | 论文 Table 2 base |
|---|---|---:|---:|
| Hangzhou1 | W，25% | 369.7748 | 369.77 |
| Hangzhou1 | W/E，50% | 722.4372 | 722.43 |
| Hangzhou2 | W，25% | 372.1280 | 372.12 |
| Hangzhou2 | W/E，50% | 533.8188 | 533.81 |

四格均相差约 0.01 秒以内，是明确的正面证据：这条 CityFlow 线的基础评测不是随意换了一个任务。更早的 SUMO/RESCO、lane count、GRU/GNN 结果可作机制探索，不能直接放进 RobustLight 同口径成绩表。

仍需区分“评测对齐”和“全部训练预算/输入对齐”：当前恢复器使用所有 16 个路口、192 个 movement slot 的联合输入和 24 步窗口；官方恢复器按路口样本使用 4 步条件。暖启动也不同：官方 `long_state_con` 从控制器实际使用的历史状态更新，初期包括干净状态；IF 始终缓存先掩蔽后的输入，并重复第一帧补齐窗口。建议把这些差别写入协议，并给出窗口长度、空间输入与暖启动消融。

## 3. 已验证的主要瓶颈：历史反馈

训练代码 `experiments/if_recover/train_if.py:49` 的 `selfcond_forward`：

1. 对整个窗口做第一遍恢复。
2. 将历史缺失位替换成第一遍预测，并标为 observed。
3. 再跑第二遍，监督末帧（另有全窗辅助损失）。

运行代码 `src/ifrec/recoverer.py:90` 的 `autoreg`：把每一次在线末帧预测缓存下来，并把其 mask 全部设为 1，后续继续引用。

两者不同：第一遍全窗恢复生成的是利用当前窗口观测重新平滑过的历史；在线缓存来自过去时刻的递归预测。误差分布、可用信息和递归深度都不相同。ImputeFormer 的时间注意力没有因果掩码，这加强了这种差异。

这里**不能笼统说在线模型偷看未来**：只输入截至当前时刻的窗口并输出末帧是合法在线推理。问题是训练生成历史预测的方法，与运行时生成历史预测的方法不一致。若在线也重新做同样的两遍平滑，这是另一个可评估方案；当前实现没有这样做。

固定 `orig_5816.npz` 干净轨迹，W 缺失，选取窗口完整的每 4 步末帧，共 55 个时刻，同一个 selfcond checkpoint：

| 推理方式 | 原始压力单位的 masked MAE |
|---|---:|
| 原始缺失历史，一遍前向 | 0.9697 |
| 训练式两遍 self-conditioning | 1.1057 |
| 部署式 autoreg 递归历史 | 2.0516 |

末帧动作与数据中的相位对齐检查为 0 个不匹配；所以这份诊断轨迹不支持“相位错一拍”解释。标准化后缺失位由模型再次乘 mask，本次也没有发现一个简单的“缺失零值未正确标准化”错误。

闭环上只切换 `autoreg`，保持同一 selfcond 权重：

| 设置（W 缺失） | Hangzhou1 ATT | Hangzhou2 ATT |
|---|---:|---:|
| 完整观测 | 288.54 | 348.98 |
| 无恢复，零填充 | 369.77 | 372.13 |
| 普通 IF checkpoint，无反馈 | 404.90 | 382.13 |
| selfcond checkpoint，开反馈 | 398.40 | 394.99 |
| **同一 selfcond checkpoint，关反馈** | **321.96** | **366.28** |
| 论文 RobustLight，作者报告 | 350.80 ± 20.22 | 353.85 ± 3.66 |

关反馈相对开反馈，ATT 分别下降约 19.2% 和 7.3%；相对无恢复分别改善约 12.9% 和 1.6%。这足以把“反馈设计”列为首要修复项，但不能推导出 self-conditioning 训练本身无用，也不能根据 Hangzhou1 单次数字宣布整体超过 RobustLight。

进一步将同一无反馈 checkpoint 用于 50% 缺失，没有针对这些结果再次选模：

| 数据集 / 缺失 | 本地无恢复 | selfcond 无反馈 | 论文 RobustLight（作者报告） |
|---|---:|---:|---:|

该配置在四格都优于本地无恢复，50% 缺失时改善更大。三格单次数字低于论文均值，只能作为值得多种子复核的线索；训练数据、空间条件、历史长度与方法随机性仍有差别，而且当前两个杭州流量已经参与了开发观察，不能包装成全新的盲测结果。

## 4. 其他需要解决的原因与协议问题

### 离线平均误差没有完整反映部署任务

普通 IF 的训练/验证对整个窗口计算损失，而部署只使用最后一帧。相同诊断时刻，普通 IF 全窗 MAE 为 1.0421，末帧为 1.2832。日志里的 MAE 还是标准化单位，当前 scaler 的标准差约 15.2227；不能直接拿日志 0.1 与闭环原始单位 2–3 比较。

训练还在结构化缺失之外叠加 20%/50%/80% 的随机 whitening。例如固定 25% 方向缺失再叠加这些概率，总缺失率期望分别为 40%/62.5%/85%。这种增强未必有害，但不等于测试的固定方向缺失，建议做关闭/减弱 whitening 的受控消融。

此外，MaxPressure 使用四个相位得分：`p1+p4`、`p7+p10`、`p0+p3`、`p6+p9`。12 个槽中的右转槽不直接参与这四个得分，平均重建损失却同样计算这些维度。接近并列的相位、关键高压力队列和服务时间会影响 ATT，不能仅追逐平均 L1。相位不同但真实得分并列时，即时压力 regret 也可能为零，应区分 tie 与真正低得分选择。

### 干净控制轨迹不能覆盖全部闭环状态

训练数据来源是完整观测 MaxPressure。48 个变体又来自同一条 5816 flow 的车辆筛选与时间扰动；默认训练 40 个变体，验证 4 个变体。这不是 40 个独立路网或独立城市。

模型错误会改变相位，继而改变拥堵与未来观测。仅在干净轨迹上人工 mask，不能自动训练出在这些偏离轨迹上稳定工作的恢复器。已有 `probe_values.npz` 中普通模型在 `|true pressure| > 10` 位的 MAE 达 19.22；这是旧 checkpoint/其他流量下的描述性证据，不能与此次固定干净轨迹直接作为严格配对比较，但足以提示关注尾部状态。

优先收集**训练流量**在 zero-fill、当前恢复器、随机探索/固定周期控制下的轨迹；恢复器只吃合法损坏观测，模拟器完整状态只作为训练监督标签。不要把测试流量的真值轨迹加入训练再报告为泛化成绩。

### 输出语义是 signed pressure，不是非负车辆数

`refs/RobustLight/utils/cityflow_env.py:254` 计算进口等待车辆数减去目标出口道路的等待车辆数，因此压力可以为负。不要把 SUMO 模型原有 `ReLU` 非负车辆数输出头原样搬过来，也不要直接使用 `log1p(pressure)`。如果复用 GRU/GNN 主干，需改为有符号输出和适配的归一化。

### mask 来源信息没有被保留

IF 的 `mask` 仅用于乘掉输入，并未作为独立特征拼接；autoreg 又把模型生成的值全部标为 observed。建议至少明确区分真实观测、模型预测和缺失，并输入距上次真实观测的时间。若保留递归，训练应按部署逻辑展开多个因果步骤，而非依赖两遍全窗前向近似。

### checkpoint 选择与监控有具体漏洞

`monitor_ckpt.sh` 每次启动将 `BEST_ATT` 重置为 99999，监控的进程 ID 硬编码，多个监控进程共享临时 checkpoint、workdir 和 best 文件。本次进程列表确实同时存在两个实例；日志也出现先记录 375.57，之后重新将 398.98 标成“new best”。因此 `best_att.pt` 文件名并不能证明它是历次全局最优。

而且该脚本直接根据原始 5816 flow 的闭环 ATT 选模型。如果把此 flow 当最终测试集，这是测试集参与选模。应另设验证 flow/训练种子，验证选定后冻结，在最终测试上一次汇报。保存 checkpoint 时记录 epoch、配置、hash；监控单实例运行、写文件用原子替换，按 run 隔离日志与路径。

### 指标名称和随机性

当前 ATT 与官方聚合方法一致，但 `n_out` 是“曾离开至少一个路口的车辆集合”，不是严格的到达网络终点车辆数；这是沿用官方 `summary.py` 的行为。另行报告真正网络完成量时要换统计接口并明确区分。

CityFlow 环境把仿真 seed 写死为 0。重复同一确定性 checkpoint 不能算多个独立训练种子。论文称报告十次独立运行；本地先做至少三个独立训练种子排查稳定性，再扩展正式矩阵，并写明训练与仿真随机源。

## 5. 建议的执行顺序

1. **先固定可用参考点。** 用本次冻结 selfcond 权重，关闭 autoreg，建立完整观测/零填充/普通 IF/selfcond 无反馈对照。先测杭州 W 与 W/E，再考虑更多模型。当前改进无需重训。
2. **把训练和验证统一到在线末帧。** 用真实运行的历史缓存逻辑做逐步验证；对纯窗口模型保留原始观测和缺失，输出末帧即可，不必机械照搬 diffusion 的递归条件。若做反馈模块，保持观测来源标记并开展短期到长期 rollout 训练。
3. **轻量动作条件模型作为候选。** 优先比较共享 GRU/TCN＋道路连接图的恢复器，输入动作、mask、观测龄和历史压力；signed 残差输出，真实观测直通。模型容量不是当前首要瓶颈；现有 IF 约 131 万参数，8 GB 显存可先用于提高训练部署一致性。
4. **再加控制相关目标。** 重建损失之外，对真实相位得分或压力 regret 建立损失，区分并列与真正误选，关注高压力尾部。闭环 ATT 必须独立验证；此前 SUMO 线已经显示离线决策指标改善未必带来 ATT 改善。不要一开始同时堆叠不确定性、风险折扣和复杂控制器。
5. **补闭环训练数据覆盖。** 在训练场景做恢复器诱导轨迹采集/数据聚合，控制训练数据预算，与纯干净轨迹训练做消融。
6. **最后扩展论文证据。** 杭州两流量、济南至少一流量，W/W-E 为主协议；其他方向作泛化验证。至少再接一种冻结控制器才能支持较广泛的 plug-and-play 主张。只做缺失就明确研究范围，不将结果外推为对抗噪声鲁棒性。

优先消融建议：普通 IF → 末帧训练 → 加 mask/来源/观测龄 → 因果 rollout 或闭环数据聚合 → 相位得分损失。逐项加，每项同时看 ATT、严重拥堵、决策 regret 与推理耗时。多模块一起加后只刷单一分数，不利于形成可解释的创新。

## 6. 更稳妥的创新定位

“将 diffusion 换成 ImputeFormer”可作基线工程，但通常不足以单独支撑方法创新。可验证的定位是：**在保持控制器与缺失评测协议不变的条件下，设计保留观测来源、训练部署一致的轻量在线恢复器，降低递归漂移，并改善交通效率与计算开销。**

这里有三个需要实验回答的问题：为什么全窗离线补全在闭环中退化；怎样防止模型预测被当成真实观测后累积偏差；同等恢复预算下，交通收益和效率是否优于通用补全基线。不要把原论文已有的动作条件、多步误差处理或控制导向概念本身重新宣称为新贡献。

不重跑 diffusion 时，论文数字单独标成“作者报告”，本地复现的 base 单独标明；当前四格 base 对齐是重要支撑，但仍不能替代对 diffusion 的本机延迟、显存或严格同预算测量。可以报告本方法的实际资源开销，不编造跨硬件加速倍数。
